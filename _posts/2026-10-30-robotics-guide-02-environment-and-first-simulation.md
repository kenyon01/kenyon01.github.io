上一章，我们为“把桌上的物体放进盒子”画了系统图。这一章先把桌面和物体放进计算机，让物体真的受重力、落下、碰到桌面，再加入机械臂。

先设想一个调试现场：你运行了程序，终端没有报错，屏幕上却没有窗口。这算运行成功吗？如果程序本来只计算物理、不创建窗口，可能已经成功。反过来，窗口里出现了漂亮的机械臂，也只能说明模型能够显示；仿真时间是否前进、物体是否参与碰撞、程序是否读取到了新状态，还要分别检查。

本章会把这些环节逐个拆开。完成以后，你应该能独立重建环境，解释一份小型模型文件，运行有窗口和无窗口两种实验，并留下别人能够复查的配置与结果。

本文使用 **MuJoCo 3.3.7、NumPy 2.3.4、Pillow 12.0.0** 作为冻结的教学版本；Python 使用 3.13 系列。这是为本章选定的一套组合，不代表当前最新版本。主线命令采用 Windows PowerShell，同时列出 Linux 的对应入口。实际验证范围写在文末，不把未测试的平台算作已通过。

可以先下载[第二章完整实验包](/article-media/robotics-guide-ch02/robotics-ch02.zip)。解压后得到 `robotics-ch02` 文件夹，里面有本文使用的 Python 程序、XML 模型、JSON 配置和运行说明。包内没有机器人驱动、训练权重和外部网格，也不需要连接真实机械臂。

## 2.1 准备可重复使用的开发环境

### 2.1.1 操作系统、终端与项目目录

先找一个固定目录存放实验，例如 Windows 下的 `D:\robotics\robotics-ch02`。把下载的实验包解压到这里，再用编辑器打开这个文件夹。不要把源码散放在下载目录，也不要直接在压缩包预览窗口中运行程序。

终端是向操作系统发出命令的入口。Windows 本章使用 PowerShell；Linux 使用 Bash 一类的 Shell。它们都能启动 Python，但路径写法、变量语法和激活环境的命令不同。从网页复制命令前，先看代码块标注的是哪一种终端。

在 PowerShell 中进入刚才的目录：

```powershell
cd D:\robotics\robotics-ch02
Get-Location
Get-ChildItem
```

第一条改变当前工作目录，第二条检查你现在在哪里，第三条列出文件。正常情况下，应能看到 `requirements.txt`、`check_install.py`、`quick_drop.py`、`run_scene.py`，以及 `models` 和 `config` 两个子目录。

这一步看起来琐碎，却能提前消掉一大类错误。`python run_scene.py` 会先让终端在当前目录寻找脚本；如果你还停留在压缩包的上一层，Python 可能根本找不到文件。后面脚本中的模型路径又是另一回事：本章程序会以脚本所在目录定位模型，避免“从编辑器运行可以，从终端运行不行”的混乱。

建议保留下面的目录关系：

```text
robotics-ch02/
├── requirements.txt
├── requirements-lock-windows.txt
├── check_install.py
├── quick_drop.py
├── run_scene.py
├── verify_lab.py
├── models/
│   ├── drop.xml
│   └── tabletop.xml
├── config/
│   ├── drop.json
│   └── tabletop.json
└── README.md
```

`.venv` 和 `runs` 会在后面的操作中生成，前者放环境，后者放结果。两者的用途不同，恢复环境时应当保留源码和结果，重新创建 `.venv`。

如果你使用 Linux，先选一个属于自己的工作目录，解压并 `cd` 进去，再用 `pwd`、`ls` 确认文件。暂时不必为了运行本章安装 ROS 2、CUDA、PyTorch 或容器。本章的两个小场景使用普通 MuJoCo 物理步进，不进行神经网络训练，也不要求占用 T4 或昇腾设备。

### 2.1.2 Python 虚拟环境与依赖管理

同一台电脑上可能已经有多个 Python。编辑器选中的解释器、终端里输入 `python` 找到的解释器、某个训练项目使用的解释器，未必是同一个。先确认版本，再创建环境，会比安装报错后反复重装省事。

Windows 如果已经安装 Python Launcher，可以检查：

```powershell
py -3.13 --version
```

如果系统没有 `py` 命令，可使用已安装的 Python 3.13 解释器完整路径代替；若使用 `python`，先运行 `python --version`，确认它确实指向准备使用的版本。没有 Python 时，从 [Python 官方网站](https://www.python.org/downloads/)选择适合自己系统的安装程序。本章按普通的 64 位 CPython 环境组织依赖，不使用 free-threaded 实验构建。

确认后，在实验根目录创建虚拟环境，并通过环境里的解释器安装依赖：

```powershell
py -3.13 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

这里故意写完整的 `.venv\Scripts\python.exe`。这样每次都能看出命令使用哪个解释器，也不必先执行 PowerShell 激活脚本。环境“激活”主要是方便终端找到解释器；直接调用环境中的 Python，同样能够使用这个环境。可以对照 [Python 的 venv 说明](https://docs.python.org/3.13/library/venv.html)理解这一点。

`requirements.txt` 的内容很短：

```text
mujoco==3.3.7
numpy==2.3.4
Pillow==12.0.0
```

MuJoCo 提供仿真与查看器，NumPy 处理数组，Pillow 仅用于把渲染图像保存为 PNG。即使暂时不生成图片，按这份文件安装也能保持整套实验入口一致。普通 `mujoco` 包已经携带对应的 MuJoCo 库，本章不再另装旧的 `mujoco-py` 绑定。[MuJoCo 安装说明](https://mujoco.readthedocs.io/en/3.3.7/python.html#installation)

Linux 的对应命令是：

```bash
python3.13 -m venv .venv
./.venv/bin/python -m pip install -r requirements.txt
```

这两组命令是不同平台的两条路径，选择自己的一组即可。Linux 上如果没有 Python 3.13，应先根据发行版准备解释器，不要把系统默认 `python3` 的版本猜成 3.13。

安装过程中若出现下载超时，先查看错误是在联网下载还是编译扩展。一次下载中断并不说明模型不支持你的显卡。本章也不需要把包安装到系统 Python、以管理员身份覆盖已有库，或者先升级整台机器的驱动。

### 2.1.3 安装检查、版本记录与环境恢复

安装完成后，先做无窗口检查：

```powershell
.\.venv\Scripts\python.exe check_install.py
```

它会输出 Python 版本、解释器路径、操作系统信息，以及 MuJoCo 和 NumPy 的版本，然后临时创建一个带自由物体的小场景，推进十个物理步。最后一行应包含 `Physics OK`。

这项检查回答了两个很具体的问题：包是否装进了正在运行的解释器，以及物理计算能否实际启动。它没有创建图形窗口，也没有测试显卡渲染，因此通过后暂时不能得出“查看器一定正常”的结论。

如果看到 `ModuleNotFoundError: No module named 'mujoco'`，先看解释器路径。下面两条命令可以检查同一解释器安装的包：

```powershell
.\.venv\Scripts\python.exe -m pip show mujoco
.\.venv\Scripts\python.exe -m pip check
```

直接使用 `pip show mujoco`，可能检查到另一套 Python 的环境。把安装和运行都写成 `同一个python -m ...`，就少了一层猜测。

随后保存自己的完整包版本快照：

```powershell
.\.venv\Scripts\python.exe -m pip freeze > requirements-local.txt
```

实验包中的 `requirements-lock-windows.txt` 是本文验证时的 Windows 包版本快照，用来说明当时实际安装了什么；`requirements.txt` 则固定本实验直接使用的三个依赖。两者不要混淆。一个平台的 `pip freeze` 也不是跨平台、带完整文件哈希的锁定方案，不能仅凭它保证所有机器得到完全相同的二进制包。

以后要恢复实验，保留源码、模型、配置、版本记录与运行结果，在新的独立环境中重新安装依赖。不要把旧 `.venv` 文件夹直接搬到另一台电脑。虚拟环境可能记录原解释器位置，也包含与操作系统相关的文件，移动文件夹不能代替重建。

如果重建后行为改变，比较时至少应列出 Python、MuJoCo、NumPy、平台、模型文件和实验配置。只写“我也是用 Python 跑的”，无法排除其中任何一项差异。

## 2.2 认识 MuJoCo 与机器人模型

### 2.2.1 物理仿真、图形显示与控制程序

为了让方块落在桌上，计算机需要知道物体的形状、质量、位置、速度以及接触关系，然后计算下一时刻会发生什么。MuJoCo 在这里承担物理计算，也提供把场景画出来的工具。[MuJoCo 概览](https://mujoco.readthedocs.io/en/3.3.7/overview.html)

我们把本章的运行过程画成三条相连的线：

![模型、物理状态与图形显示之间的数据关系](/article-media/robotics-guide-ch02/simulation-pipeline.svg)

*图 2-1：XML 先编译成模型，模型与运行状态一起进入物理计算；查看器和日志读取计算结果。显示窗口没有替代物理步进。*

**模型文件**负责描述场景。它可以声明桌面的尺寸、方块的质量、关节的运动轴和相机位置。它并不等于一段预录好的动画。

**运行状态**保存当前情况，例如已经推进的仿真时间、物体位置和速度。程序每推进一步，就可能修改这些数值。

**图形显示**把某一时刻的状态画成图像。相机视角变了，同一状态可以显示成不同画面；关掉显示，也不妨碍程序继续做不依赖渲染的物理计算。

**控制程序**决定怎样施加控制输入、什么时候推进、什么时候记录和停止。后面我们会用 Python 给关节目标。本章先不添加执行器，让方块的变化只来自重力和接触，减少排错时需要考虑的因素。

第一次实验时，建议把“能导入包”“能计算物理”“能创建图形上下文”“画面符合预期”分开检查。例如：

| 观察到的现象 | 目前能够说明什么 | 下一项检查 |
| --- | --- | --- |
| `import mujoco` 不报错 | 当前解释器能够导入绑定 | 真正加载并推进一个模型 |
| 仿真时间前进、方块位置改变 | 至少这段物理计算能够运行 | 落桌后的位置和接触是否合理 |
| 窗口显示模型 | 图形入口能够创建并绘制场景 | 当前程序是否在推进时间 |
| 方块稳定在桌面附近 | 这组参数下出现了支撑接触 | 查看记录，确认尺寸、坐标和误差 |

这张表也能帮助判断硬件需求。本章数十个几何元素以内的小场景，没有必要先搭建多卡训练系统。图形显示确实需要合适的驱动和图形环境，但这里的渲染需求与神经网络训练显存是两件不同的事。

### 2.2.2 MJCF 文件与最小模型结构

MuJoCo 的原生模型格式叫 **MJCF**，使用 XML 语法。初看时容易被尖括号和属性名挡住，其实可以先按“全局设置 → 世界 → 物体 → 物体允许的运动”读下来。

下面是实验包中 `models/drop.xml` 的完整内容：

```xml
<mujoco model="falling_cube">
  <compiler angle="radian"/>
  <option timestep="0.002" gravity="0 0 -9.81"/>
  <visual><global offwidth="960" offheight="640"/></visual>
  <worldbody>
    <light pos="0 -1 3" dir="0 0 -1" directional="true"/>
    <camera name="overview" pos="1.4 -1.8 1.45"
            xyaxes="0.789 0.614 0 -0.269 0.346 0.899"/>
    <geom name="floor" type="plane" size="2 2 0.1" rgba="0.19 0.23 0.28 1"/>
    <geom name="table" type="box" pos="0 0 0.35" size="0.55 0.40 0.35"
          rgba="0.65 0.72 0.76 1"/>
    <body name="cube" pos="0.20 0 0.95">
      <freejoint name="cube_free"/>
      <geom name="cube_geom" type="box" size="0.02 0.02 0.02"
            mass="0.08" rgba="0.95 0.55 0.15 1"/>
    </body>
  </worldbody>
</mujoco>
```

先看最外层 `<mujoco>`，它包住整个模型。`compiler angle="radian"` 明确 XML 中相关角度属性采用弧度；`option` 设定每次物理更新对应 `0.002 s`，并指定向下的重力。

`worldbody` 是世界中的物体树。直接写在这里的地面和桌面几何体是固定环境；方块则放在一个 `body` 内，并通过 `freejoint` 获得自由平移和转动的能力。不要认为只要给几何体涂了橙色，它就会自动变成能够掉落的物体。

`geom` 定义几何形状及相关物理属性。方块的 `type="box"` 表示长方体，`size="0.02 0.02 0.02"` 给的是沿三个轴的**半尺寸**，所以实际边长是 `0.04 m`，即 40 mm。桌面的中心在 `z=0.35 m`，竖直半尺寸也是 `0.35 m`，其上表面因此位于 `z=0.70 m`。

方块初始中心位于 `z=0.95 m`，底面位于 `0.93 m`，与桌面之间有 0.23 m 间隙。如果它最终受到桌面支撑、不发生明显穿透，中心高度应接近 `0.70+0.02=0.72 m`。这个数可以在真正运行前先算出来，后面用它检查输出。

`light` 与 `camera` 用于显示，`visual` 中的宽高则为本章离屏渲染预留缓冲区。它们不会赋予方块新的运动自由度。相机的朝向写法本章先沿用，坐标变换到第 4 章再展开。

不要一次记住所有属性。先能指出谁是固定环境、谁能运动，哪个数决定时间步长，哪个数决定物体尺寸，就已经有了阅读模型的入口。属性的精确定义可随时对照 [MJCF XML 参考](https://mujoco.readthedocs.io/en/3.3.7/XMLreference.html)。

### 2.2.3 模型参数与运行状态的区别

加载 XML 后，Python 中会出现两类对象：`MjModel` 与 `MjData`。可以先把它们理解为“编译后的场景定义”和“这一次运行所使用的状态与计算空间”。

| 放在哪一侧 | 本章会接触的内容 | 改动的含义 |
| --- | --- | --- |
| `model` | 时间步长、重力、关节类型、几何尺寸、物体质量 | 改变所模拟系统的定义或求解设置 |
| `data` | 仿真时间、广义位置、广义速度、接触和派生量 | 改变或读取本次运行的情况 |

例如，方块质量为 `0.08 kg` 是模型参数；它现在位于桌面上方 0.25 m、正在向下运动，是运行状态。同一份模型可以创建多份 `MjData`，让它们从不同初始位置运行，但状态必须与对应模型匹配。[MuJoCo 仿真初始化说明](https://mujoco.readthedocs.io/en/3.3.7/programming/simulation.html#initialization)

接下来会看到 `model.nq`、`model.nv` 和 `model.nu`。它们分别表示广义位置数组长度、广义速度数组长度和控制输入数量。注意这里说的是**数组长度**。

本章自由方块的 `nq=7`、`nv=6`：位置使用三个平移分量与四元数的四个分量，速度使用三个线速度分量与三个角速度分量。因此，不能把 `len(data.qpos)` 直接当成物理自由度，也不能假定位置与速度的数组长度相等。四元数有约束，其四个数并不代表四个独立旋转自由度。

`nu=0` 则说明模型没有控制输入。它并不意味着场景不能变化。方块没有电机，仍然可以受重力下落。相反，如果以后模型声明了执行器，控制数组里的数字才需要按执行器定义解释。

还有一类经常读到的是派生量，例如物体在世界坐标系中的位置 `data.body("cube").xpos`。它由当前状态经过计算得到。修改了 `qpos` 后，不应假设所有位置、接触或传感器输出都已自动刷新；后面会调用 `mj_forward`，让模型在当前状态下重新计算相关量。

本章不通过运行过程中随意修改模型质量或几何尺寸来做实验。先改 XML、重新加载，再比较结果，变化来自哪里会更清楚。某些模型字段运行时可修改，但其他依赖量是否需要更新，要另查相应接口，不能把 `model` 当成任意改完立即生效的字典。

## 2.3 运行第一个物理场景

### 2.3.1 加载模型并创建运行数据

现在打开 `quick_drop.py`。这个程序保留了最短的一条物理运行路径：找到 XML、加载模型、创建状态、检查初始量、推进，再读取结果。

```python
"""The short physics example printed in section 2.3."""

from pathlib import Path

import mujoco

root = Path(__file__).resolve().parent
model = mujoco.MjModel.from_xml_path(str(root / "models" / "drop.xml"))
data = mujoco.MjData(model)
mujoco.mj_forward(model, data)

print("nq, nv, nu:", model.nq, model.nv, model.nu)
print("start:", data.time, data.body("cube").xpos.copy())

for _ in range(1000):
    mujoco.mj_step(model, data)

mujoco.mj_forward(model, data)
print("end:", data.time, data.body("cube").xpos.copy())
print("contacts:", data.ncon)
```

在 PowerShell 中运行：

```powershell
.\.venv\Scripts\python.exe quick_drop.py
```

第一段路径代码值得慢慢看。`__file__` 是当前脚本文件的位置；`resolve().parent` 取得它所在目录。随后用 `/ "models" / "drop.xml"` 拼接路径。这里的 `/` 是 `Path` 的路径组合写法，不是数字除法。

`MjModel.from_xml_path(...)` 会读取、解析并编译模型。它可能在这一步就报告 XML 语法、未知属性、文件缺失或物理参数不合法。此时还没有运行到物理循环，排错应先围绕模型加载进行。

`MjData(model)` 为这份模型建立运行数据。接着的 `mj_forward` 在不推进时间的情况下计算初始派生量。于是，第一次读取方块的世界位置时，读到的是已经根据初始构型更新过的值。

对于 `drop.xml`，第一次输出应显示 `nq, nv, nu` 为 `7 6 0`。没有随机扰动的短程序中，方块初始位置来自 XML，即 `[0.20, 0, 0.95] m`。这些都是能够逐项核对的证据，比终端中单独一句“运行成功”更有用。

创建模型与创建数据的关系也限制了使用方式。以后换成包含机械臂的新模型，就应重新创建对应的 `MjData`。不要把旧场景的数据塞给新模型，即使两者看起来都包含一张桌子。

### 2.3.2 推进仿真时间并读取状态

`for` 循环执行了 1000 次 `mj_step`。本例步长为 `0.002 s`，所以覆盖的仿真时间是：

```text
1000 × 0.002 s = 2.000 s
```

这说的是被模拟的时间，不是你在现实中一定等待了两秒。没有显示和节拍等待时，程序可能更快结束；机器较慢或加入其他计算时，也可能更久。比较速度前，必须把仿真时间与现实耗时分别记录。

循环后再次执行 `mj_forward`，是为了让这里要读取的世界坐标等派生量对应步进后的状态。`mj_step` 会完成物理推进，但一些中间结果对应其计算流水线中的特定阶段；本章采用显式刷新后再记录的写法，避免把“新关节位置”和“先前计算的物体位置”混在同一行日志里。[MuJoCo 主要仿真函数](https://mujoco.readthedocs.io/en/3.3.7/APIreference/APIfunctions.html#main-simulation)

观察终端时，先核对以下四项：时间接近 `2.0 s`；方块中心高度从 `0.95 m` 降低；最终高度接近之前计算的 `0.72 m`；最后存在接触。浮点输出可能写成 `2.0000000000000013`，不必因此认为时钟坏了。

最终高度也不要求小数点后每一位都等于 `0.72`。接触模型、求解精度与数值积分会引入小偏差。真正应该引起注意的是方块仍停在 0.95 m、穿过整张桌子，或者出现 `nan`、`inf` 这样的无效数值。

![本章模型在两秒物理计算后的方块与桌面](/article-media/robotics-guide-ch02/falling-cube.png)

*图 2-2：由本章 XML 和 MuJoCo 渲染器生成的场景图。终端中的数值检查与这张图应当相互对应；一张图片本身不能说明前面的下落过程。*

最后看 `.copy()`。MuJoCo 的一些数组接口直接映射到底层内存。若把 `xpos` 的引用连续追加到列表，后续更新可能让多个列表元素看起来都变成最后一次的值。记录历史时，应当复制数组或马上转成独立数值。本章完整程序把每一步的位置复制后写入 CSV，因此保留的是各个时刻的样本。

### 2.3.3 打开查看器、调整视角与关闭程序

数值路径通过后，再打开窗口：

```powershell
.\.venv\Scripts\python.exe -m mujoco.viewer --mjcf=models/drop.xml
```

这个命令使用 MuJoCo 自带的独立查看器。路径相对于当前工作目录，因此仍要站在实验根目录执行。这里先用它检查桌面、方块、视角与图形环境。[独立查看器入口](https://mujoco.readthedocs.io/en/3.3.7/python.html#standalone-app)

窗口出现后，尝试拖动鼠标旋转视角，用滚轮改变观察距离。若操作与本文描述不同，查看窗口帮助中的鼠标操作说明；不同窗口系统和输入设备可能影响组合键。先绕着桌子观察，确认方块在桌面上方，而不是靠一张正面图判断空间关系。

不要通过把镜头移近来修正模型尺寸。镜头改变的是观察方式；如果桌面被写成 70 m 高，换个视角也不会把物理尺寸变回 0.70 m。遇到场景特别巨大或特别微小时，回到 XML 检查单位与半尺寸。

接下来使用完整脚本的图形模式：

```powershell
.\.venv\Scripts\python.exe run_scene.py
```

这次由 Python 程序推进物理，并用 `launch_passive` 创建查看器。在每次更新后，脚本调用 `viewer.sync()`，让显示与交互状态同步。它还根据物理步长做简单等待，使观察时的速度接近现实节奏；这只是教学用节拍，不是严格的实时调度。

被动查看器与程序存在并发关系。实验包的实现按文档要求，在修改模型、状态与相机设置时使用 `viewer.lock()`，同步调用放在锁外。初学时先保留这段完整写法，不要把锁和同步语句随意删掉。[被动查看器说明](https://mujoco.readthedocs.io/en/3.3.7/python.html#passive-viewer)

配置默认只运行 2 秒，所以脚本窗口很快关闭是预期行为。想多观察一会儿，可以把相应 JSON 中的 `seconds` 改成 `10.0`，再运行；或用前面的独立查看器检查模型。提前关闭脚本窗口会结束本次循环，运行摘要中的 `complete` 会是 `false`，不能把中断当成完整跑完。

本章主线面向 Windows 与 Linux。若迁移到 macOS，被动查看器还有主线程要求，官方要求使用随包安装的 `mjpython` 启动相应脚本；不能把 Windows 的解释器路径原样复制过去。

## 2.4 让实验可以重复启动

### 2.4.1 初始化、复位与初始状态

第一次运行时，方块从空中落下；如果想在同一程序里再做一次，不能只把仿真时间设回零。物体已经在桌面上，速度、接触和其他运行量也可能与第一次不同。时钟归零并没有让世界回到起点。

本章的 `reset_scene` 先调用 `mj_resetData(model, data)`，再施加本次配置规定的初始位置，最后执行 `mj_forward`。可以把它理解成三个连续动作：恢复模型的默认运行数据、应用本回合的设定、更新由设定推导出的量。

核心部分如下，完整版本还检查机械臂初始角是否位于关节范围内：

```python
mujoco.mj_resetData(model, data)
rng = np.random.default_rng(config["seed"])
cube_adr = model.joint("cube_free").qposadr[0]
data.qpos[cube_adr:cube_adr + 2] += rng.uniform(
    -config["cube_xy_jitter_m"],
    config["cube_xy_jitter_m"],
    size=2,
)
mujoco.mj_forward(model, data)
```

这里通过关节名称找到方块在 `qpos` 中的起始位置。没有直接把 `data.qpos[0:2]` 当成永久约定，是因为加入其他关节、调整模型顺序后，数组布局可能改变。按名称访问的习惯，从第二章就可以建立起来。

本例只扰动方块的水平位置，竖直初始高度仍取 XML 中的 `0.95 m`。若要设置自由物体的朝向，还需要处理四元数及其归一化；先不要把七个位置分量全部填成零。零向量不是一个有效的单位四元数。

`mj_resetData` 恢复的是模型所规定的默认状态，它不会替你重置 Python 程序自己的变量。将来如果加入阶段计数器、策略历史、累计奖励或图像缓存，这些内容也要在回合开始时清空。仿真器复位与整个任务程序复位，需要分别检查。

实验包的 `verify_lab.py` 做了一项有意义的往返检查：记录初始状态，推进 1000 步，再使用同一个配置复位；检查时间回到零、速度归零、初始广义位置与先前一致。这样才证明程序能够回到起点，而不是仅仅再次调用了一个名字叫 reset 的函数。

### 2.4.2 图形运行与无窗口运行

完整程序有两种基本运行方式：

```powershell
# 只计算物理，不创建查看器
.\.venv\Scripts\python.exe run_scene.py --headless

# 使用程序驱动的查看器观察同一场景
.\.venv\Scripts\python.exe run_scene.py
```

两者读取同一份模型和配置。无窗口分支逐步计算并记录；图形分支另外创建查看器、同步显示，并加入节拍等待。程序没有因为“不看画面”就移除重力或桌面碰撞。

这里必须分清三个经常都被称为“无头运行”的需求：

| 需求 | 本章对应入口 | 是否需要图形上下文 |
| --- | --- | --- |
| 只算物理、保存数值 | `--headless` | 本程序不创建图形上下文 |
| 显示交互窗口 | 默认图形模式或独立查看器 | 需要桌面及可用图形环境 |
| 不显示窗口，但输出相机图片 | `--headless --render` | 渲染仍需要图形上下文 |

最后一行最容易误判。没有可见窗口，不等于完全不依赖图形栈。离屏渲染仍然要创建渲染上下文；Linux 服务器上选择 EGL、OSMesa 等后端，还涉及系统库和对应运行环境，不能只加一个 `--headless` 就认为问题已解决。

实验包只有显式添加 `--render` 时才创建渲染器，并在上下文管理器结束时释放资源。默认无窗口分支不导入查看器模块，也不初始化渲染器。它适合作为远程机器上排查“到底是物理失败，还是显示失败”的第一条路径。

若你使用 T4 服务器，可先通过 SSH 跑纯物理命令，查看 CSV 与摘要，再处理渲染。若使用昇腾服务器，也应先检查机器的 CPU、操作系统和 Python 包是否支持本章环境；不能因为有 NPU 就推断普通 MuJoCo 会把物理计算自动转移到 NPU。本章没有训练代码，也没有 NPU 后端适配步骤。

图形模式中的现实耗时还包含建窗、同步和等待，因此不能拿它与纯物理循环的耗时直接比较“物理引擎快了多少倍”。要比较计算性能，先统一是否渲染、记录频率、模型与计时范围。

### 2.4.3 配置、随机种子与输出目录

打开 `config/drop.json`，可以看到本次实验选择了哪个模型、运行多久、使用哪个随机种子，以及初始位置允许偏移多少：

```json
{
  "model": "models/drop.xml",
  "seconds": 2.0,
  "seed": 42,
  "cube_xy_jitter_m": 0.02,
  "joint_positions_rad": {}
}
```

`cube_xy_jitter_m=0.02` 表示相对 XML 中的水平坐标，分别在 x、y 方向加入 `[-0.02, 0.02] m` 范围内的随机偏移。它不是把方块位置固定设成 0.02 m，也不是标准差为 0.02 m 的高斯噪声。把分布与单位写清楚，后面比较不同布局才有依据。

程序在每次复位时，根据 `seed` 新建局部随机数生成器。因此，相同配置会从同样的随机序列起点抽取位置，适合重复检查；如果想让每个回合出现不同位置，就要有意改变种子或设计连续使用生成器的机制。不要一边在每回合固定重建相同种子，一边期待场景自动变化。

种子也不是复现的全部。换了模型、NumPy 版本或初始化调用顺序，不能只靠一个 `42` 解释全部差异。跨平台的逐位一致更不能由这个简单例子保证。本章要求的是把配置与状态保存下来，使差异能够被查找。

每次运行会新建一个 `runs/<场景名>-<UTC时间>/`，避免第二次覆盖第一次的结果。目录中有三份基本文件：

| 文件 | 保存内容 | 用来回答的问题 |
| --- | --- | --- |
| `config.json` | 这次读取的配置副本 | 当时用的是哪个种子与模型？ |
| `trajectory.csv` | 时间与方块世界位置 | 方块怎样从空中落到桌面？ |
| `summary.json` | 版本、模型哈希、步数、完成状态与最终位置 | 是否执行完、结果对应哪组文件？ |

若使用 `--render`，还会生成 `final-frame.png`。它只是最终一帧，不是全程视频。

CSV 首先写初始样本，然后每推进一步写一个样本。因此，1000 个物理步对应 1001 行数据，再加一行表头。不要把“文件有 1002 行”误认为多执行了两个物理步。

摘要中的 `complete` 只表示计划步数已经执行完，与抓取成功无关。`loop_wall_time_s` 是本程序注明范围内的现实耗时；摘要还保留了本机解释器路径，公开自己的运行记录前可按需要去掉该路径。模型哈希在本章覆盖入口 XML 与已知的直接 include；以后添加网格、纹理和更多嵌套文件时，应扩充依赖记录。

## 2.5 实验 创建桌面与机械臂场景

### 2.5.1 从简单几何体搭建实验桌面

现在回到桌面本身，做一次有目的的尺寸核对。很多“物理参数不对”的现象，最初其实来自几何尺寸或坐标填写错误。

本例固定了下列几何关系：

| 元素 | 中心或参考位置 | 尺寸 | 可检查的结果 |
| --- | --- | --- | --- |
| 地面 | z=0 | 平面显示范围按模型设置 | 桌体底部位于地面处 |
| 桌体 | z=0.35 m | 全长 1.10 m、全宽 0.80 m、全高 0.70 m | 上表面 z=0.70 m |
| 方块 | 初始中心 z=0.95 m | 边长 0.04 m、质量 0.08 kg | 初始底面 z=0.93 m |
| 方块静止支撑目标 | 桌面上方 | 中心应接近 z=0.72 m | 允许小的接触求解偏差 |

桌体在这里是一整个固定长方体，不是带四条桌腿的详细家具模型。它的作用是提供明确的支撑面。以后加机械臂基座、容器或障碍物时，再逐步细化不影响当前检查的部分。

先运行标准配置：

```powershell
.\.venv\Scripts\python.exe run_scene.py --headless
```

打开新生成的 `summary.json`，核对 `requested_steps=1000`、`completed_steps=1000`、`complete=true`、`state_finite=true`。最终 `cube_position_m` 的第三个值应接近 `0.72`。前两个值受随机位置扰动影响，不必与 `quick_drop.py` 的固定起点完全相同。

再做一个对照实验：复制整个实验文件夹或单独保存模型版本，把 `models/drop.xml` 中方块的初始高度从 `0.95` 改为 `1.10`，其他设置不变，重新运行。观察开始下落的位置、接触发生的时间，以及最后支撑高度。初始高度变了，静止后由桌面和方块尺寸决定的高度不应随之抬高。

用忽略空气阻力和接触的自由落体公式，可以粗估原设定首次到达桌面的时间：`sqrt(2×0.23/9.81)`，约 `0.217 s`。这是按连续自由落体计算的参考值，不是逐步求解后必须精确出现的接触时间。你可以在 CSV 中寻找下降趋势转变的位置，再结合接触记录做更严格的分析；本章摘要没有保存全程接触事件，不能凭最终 `ncon` 反推准确的首次接触时刻。

接着把 `cube_xy_jitter_m` 改为 `0.0` 重跑，比较方块初始水平位置。这里一次只改一个因素：这样才知道结果变化来自初始高度还是水平扰动。完成对照后，恢复标准模型与配置，再继续加入机械臂。

### 2.5.2 加载机械臂并检查模型依赖

桌面场景稳定后，运行另一个配置：

```powershell
.\.venv\Scripts\python.exe run_scene.py --config config/tabletop.json --headless
```

这次入口模型是 `models/tabletop.xml`。它先通过 `<include file="drop.xml"/>` 引入已有桌面、方块、灯光与相机，再添加一条三关节运动学链：底座偏航、肩关节、肘关节。

这是一台为本章编写的**教学机械臂**，使用圆柱、胶囊体和球体构成，不对应某个商业产品。它没有夹爪，没有电机执行器，也没有抓取程序。末端橙色球用于标出工具位置，不能把它当成会自动吸附物体的抓取装置。

![桌面、自由方块与三关节教学机械臂](/article-media/robotics-guide-ch02/tabletop-arm.png)

*图 2-3：由随文模型实际渲染的桌面场景。机械臂的各运动连杆设置了重力补偿，帮助本章在没有控制器的情况下检查模型与初始姿态；这还不是驱动器或控制算法的验证。*

理解几行模型片段，就能读出结构：

```xml
<body name="upper_arm" pos="0 0 0.06" gravcomp="1">
  <joint name="shoulder" type="hinge" axis="0 1 0"
         range="-1.5 1.5" damping="1"/>
  <geom type="capsule" fromto="0 0 0 0.20 0 0"
        size="0.018" mass="0.30"/>
  <body name="forearm" pos="0.20 0 0" gravcomp="1">
    <!-- 肘关节与前臂几何体见完整模型 -->
  </body>
</body>
```

`body` 的嵌套关系表示父子结构。前臂挂在上臂末端，改变肩关节会带着前臂一起改变位置；不是把两个独立物体在屏幕上摆得相邻。`axis` 规定关节轴，`range` 限定角度范围，`mass` 指定质量。

`gravcomp="1"` 需要单独说明：本例给每个运动连杆设置重力补偿，让引擎施加对应的补偿作用，便于在初始姿态观察结构。这是明确加入的仿真辅助设定。它不会凭空变出执行器，也没有验证机械臂在真实重力下怎样靠电机保持姿态。以后学习驱动与控制时，应重新处理这一设定，不能拿本章的静止画面证明控制器有效。

初始关节角保存在 `tabletop.json` 中：底座 `0.0 rad`、肩关节 `-0.6 rad`、肘关节 `1.0 rad`。复位函数通过名字找到相应关节，再写入它的位置。本章还不要求计算末端精确位姿，只检查关节映射与模型链条。

这份模型加载后的尺寸应为 `nq=10`、`nv=9`、`nu=0`：自由方块贡献 7 个位置分量和 6 个速度分量，三个转动关节各贡献一个位置与一个速度分量。没有执行器，所以控制输入数量仍为零。

再检查文件依赖。只复制 `tabletop.xml` 到别处会缺少 `drop.xml`；程序不能靠文件名猜出被包含的桌面模型。完整实验包保留了二者的相对位置，因此 `include` 可以找到目标。以后换用外部机械臂模型，还可能依赖网格、纹理、其他 XML、模型许可证与单位约定，不能只下载最外层文件。

本章刻意不用外部网格，正是为了让第一次加载失败时，问题集中在路径、XML 和模型定义上。模型越复杂，这份依赖检查清单越有价值。

### 2.5.3 常见安装问题与本章完成检查

遇到报错时，先判断失败发生在哪一步：解释器启动、导入包、加载模型、推进物理，还是创建图形上下文。根据阶段缩小范围，比连续执行一串重装命令更容易找到原因。

| 现象 | 先核对什么 | 本章可以立即采取的动作 |
| --- | --- | --- |
| `py` 不存在或找不到 3.13 | 解释器是否安装、启动命令是否匹配 | 用已经确认版本的完整解释器路径创建环境 |
| 找不到 `mujoco` | 运行与安装是否使用同一 Python | 用 `.venv` 内的解释器执行 `-m pip show mujoco` |
| 包下载超时 | 网络、下载源与错误阶段 | 重试下载，必要时选择可信镜像；保留版本约束 |
| 没有匹配的 wheel 或尝试源码编译 | Python 版本、系统架构、包版本是否匹配 | 先核对本章组合，不盲目增加编译依赖 |
| 找不到 XML 或 include 文件 | 当前目录、脚本定位与文件相对关系 | 按完整包目录运行，检查 `models/drop.xml` 是否仍在 |
| XML 属性或质量惯量报错 | 编辑是否破坏语法或物理定义 | 回到未修改的原始模型，先验证最小场景 |
| 纯物理通过，窗口失败 | 桌面、显示会话、OpenGL 与驱动 | 把显示错误单独处理，继续保留数值验证入口 |
| 窗口出现但过程不更新 | 哪一方推进物理，是否调用同步 | 对照 `run_scene.py` 的步进和 `viewer.sync()` |
| 方块位置没有变化 | 是否加载了正确模型、是否真的步进 | 查看时间、自由关节和前后位置 |
| 日志中的历史位置全一样 | 是否保存了同一数组引用 | 在记录时复制数组或转成独立数值 |
| 第二次实验无法回到起点 | 是否完整复位状态与程序变量 | 对照 `reset_scene`，再运行往返自检 |

如果使用远程终端，没有桌面窗口本身不是异常。先要求 `--headless` 能留下有效结果，再决定是否配置远程桌面或离屏渲染。也不要因为图形错误就直接修改模型质量、碰撞参数或物理时间步长，这些修改无法补上缺失的显示环境。

完成下面六项练习，再检查自己的实验目录。

**练习一：解释模型。** 为什么桌面固定不动，而方块会落下？如果删除方块的 `freejoint`，它还会像原来一样自由落体吗？

**练习二：计算尺寸。** 桌体中心高度为 0.35 m，竖直半尺寸为 0.35 m，方块半尺寸为 0.02 m。方块被桌面稳定支撑后，中心高度为什么应接近 0.72 m，而不是 0.70 m？

**练习三：计算时间与行数。** 时间步长 2 ms，运行 2 s，一共推进多少步？如果同时保存初始状态和每步结束状态，CSV 有多少行数据、多少行表头？

**练习四：区分两种无窗口需求。** 一台服务器能够运行 `--headless`，但 `--headless --render` 失败。这是否足以说明物理计算不可用？还需要检查哪一层？

**练习五：检查随机性。** 使用 seed=42 连续复位两次，为什么方块水平位置一致？如何用 seed=43 检查扰动确实不是写死的常量？

**练习六：解释机械臂。** 加入三个转动关节后，为何 `nq` 从 7 变成 10，`nv` 从 6 变成 9，而 `nu` 仍然是 0？画面中机械臂保持初始姿态，是否证明位置控制器已经调好？

**参考分析**

1. 桌面是固定在世界中的几何体；方块所在刚体通过自由关节获得运动能力。删去该自由关节且没有其他运动关节时，方块不会继续按原来的自由刚体方式落下。
2. 桌面上表面在 0.70 m，方块中心还要比接触底面高一个半边长 0.02 m。因此目标中心高度接近 0.72 m，接触求解允许小偏差。
3. 一共 1000 步。记录初始样本后，每步再记一条，得到 1001 行数据和 1 行表头，总共 1002 行。
4. 不能。纯物理和离屏图形使用不同环节。应检查渲染上下文、图形后端和系统库，保留已经通过的物理证据。
5. 本例复位时用相同种子新建生成器，抽样起点也相同。更换种子后比较初始水平位置，可以检查它是否随配置变化；不要只比较最终高度，因为不同水平位置的方块都可能落到同一平面上。
6. 三个转动关节各增加一个位置与一个速度分量。`nu` 对应执行器控制输入，本例没有声明执行器。机械臂设置了重力补偿，静止画面不能证明已经实现目标跟踪或调好控制器。

最后在实验根目录执行自检：

```powershell
.\.venv\Scripts\python.exe verify_lab.py
```

它分别检查两个模型的数组尺寸、1000 步后的时间、状态数值是否有限、方块落桌高度与接触，以及复位、相同种子重现和更换种子后的初始差异。通过时，两份配置都会输出一行 `OK`。它不检查真实机械臂，不验证抓取，也不替代显示窗口的检查。

本章应当留下的成果是：一个可重建的独立环境；两个能够加载的模型及其配置；至少一份完整数值轨迹与摘要；一份对两种运行方式的说明。你还应能指着这些文件回答：哪个文件决定物体质量，哪个数字控制步长，哪个函数推进时间，以及第二次实验怎样回到同样的起点。

下一章再给机械臂添加明确的执行器接口，用 Python 发出第一条控制指令，比较目标与实际响应。本章的 `nu=0` 正好是那一步的起点：模型已经建立，控制关系还需要亲手补上。
