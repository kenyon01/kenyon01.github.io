第二章的机械臂已经出现在桌面上，但它还没有执行器。我们为连杆开启重力补偿，先把模型加载、物理计算和观察显示这些事情检查清楚。这一章撤掉那层辅助设定，给三个关节接上位置伺服，再从 Python 发出真正参与物理计算的控制输入。

本章的第一个目标很小：让底座转动一段角度，再回到起始方向。之后，让肩关节和肘关节一起运动。每次运行，都保留“什么时候要求它去哪儿”“随后测到了什么”“为什么停止”这三类信息。

如果画面中的机械臂转了一下，你还需要能从记录里指出：转的是哪个关节，指令用什么单位，位置误差怎样变化，最后是否真的回来了。等这些关系清楚，再去讨论末端移动和抓取，程序才有可以核对的依据。

本章继续使用 **Python 3.13、MuJoCo 3.3.7、NumPy 2.3.4**，绘图增加 **Matplotlib 3.10.7**。它们是随文实验冻结的版本，不是最新版声明。示例仍然只连接仿真，不连接真实机械臂。

先下载[第三章完整实验包](/article-media/robotics-guide-ch03/robotics-ch03.zip)，解压得到 `robotics-ch03` 文件夹。模型文件已经包含在包内，不要求你先把第二章的目录拼装过来。进入该文件夹，在 PowerShell 中准备环境：

```powershell
py -3.13 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe inspect_state.py
```

Linux 中的对应解释器路径为 `./.venv/bin/python`，先用已经安装的 Python 3.13 创建环境。本章主线沿用 PowerShell 写法；环境创建和包下载的排错可回看第二章，不需要为关节控制另外安装训练框架。

## 3.1 读取机器人当前状态

### 3.1.1 按名称查找关节、执行器与末端

先运行 `inspect_state.py`，暂时不让机械臂运动。它会打印三个关节的名称、编号、位置与速度数组中的地址，以及对应执行器的编号。

本章统一采用以下顺序描述机械臂：

```python
JOINTS = ("base_yaw", "shoulder", "elbow")
ACTUATORS = ("yaw_servo", "shoulder_servo", "elbow_servo")
```

这里有两个不同的清单。第一个列出要观察的关节，第二个列出给这些关节提供控制作用的执行器。同样位于肩部，不意味着关节编号一定等于执行器编号。

在本章的模型中，解析结果是：

| 关节 | 关节编号 | `qpos` 地址 | `qvel` 地址 | 对应执行器 | 执行器编号 |
| --- | ---: | ---: | ---: | --- | ---: |
| `base_yaw` | 1 | 7 | 6 | `yaw_servo` | 2 |
| `shoulder` | 2 | 8 | 7 | `shoulder_servo` | 0 |
| `elbow` | 3 | 9 | 8 | `elbow_servo` | 1 |

为什么有这么多不同的数字？因为方块的自由关节在机械臂之前，占用了七个广义位置分量和六个广义速度分量；而 XML 中执行器的排列顺序又是肩、肘、底座。表中的数字来自实际模型，不能当成其他机械臂的通用下标。

程序建立映射时，使用的是名称查询：

```python
qadr = np.array([model.joint(name).qposadr[0] for name in JOINTS])
vadr = np.array([model.joint(name).dofadr[0] for name in JOINTS])
aids = np.array([model.actuator(name).id for name in ACTUATORS])
```

`qposadr` 告诉我们位置数据从哪里开始，`dofadr` 对应速度数据，执行器 `id` 则对应控制数组。程序还核对每个执行器连接的关节，避免名字对应、物理连接却接错。[MuJoCo Python 按名称访问](https://mujoco.readthedocs.io/en/3.3.7/python.html#named-access)

末端也需要名字。本章在前臂末端设置了 `site name="tip"`，它是一个定位标记，可以读取世界位置，用来记录工具走过哪里。它没有抓取能力，不会因为取名叫 tip 就自动生成夹爪或接触控制。

把这些名字集中定义，会比在控制循环里四处写 `data.ctrl[2]` 更容易检查。以后替换模型时，先重新解析映射，再核对实际结构；不要让上一次实验的数组下标变成下一台机器的隐含接口。

### 3.1.2 读取关节位置、速度和仿真时间

有了映射，就可以按统一顺序读取状态：

```python
q = data.qpos[qadr].copy()
qvel = data.qvel[vadr].copy()
simulation_time = float(data.time)
tip_xyz = data.site("tip").xpos.copy()
```

前三个关节的位置单位为 rad，速度为 rad/s，时间为 s。`tip_xyz` 的三个数表示末端标记在世界坐标系中的位置，单位为 m。这里读到的还是仿真模型中的精确数值，没有加入编码器噪声和通信延迟；以后连接设备时，不能沿用“每次读到的都是当前真值”这个假设。

本章初始关节位置设为 `[0.0, -0.6, 1.0] rad`。初始化时既设置关节构型，也给执行器同样的目标，然后重新计算派生量。这样启动的一瞬间，程序没有故意要求肩和肘先转回零位。

位置和速度要一起看。假设某次测得底座为 `0.24 rad`，目标为 `0.25 rad`，位置误差只有 `0.01 rad`。但如果它仍以 `0.8 rad/s` 朝同一方向运动，不能立刻断言它已经稳定到位。它可能下一瞬间就超过目标。

这也解释了为什么日志同时记录位置、速度和时间。单独一张终点截图看不到它是否在摆动，单独一个位置数值也看不到它正在靠近还是离开目标。

读取世界位置时，本章先执行 `mj_forward`，使派生坐标与正在记录的构型对应。尤其在直接设置初始 `qpos`、恢复状态或刚做完一个记录区间后，要清楚读到的量属于哪一时刻。第二章已经用方块位置演示过这个问题，现在只是把对象换成关节和末端。

保存历史样本还需要得到独立数值。NumPy 的某些索引操作会产生副本，某些会得到视图；MuJoCo 的接口也有直接映射底层内存的情况。本章在记录边界统一 `.copy()`，再写 CSV 或 NPZ，不依赖读者记住每一种索引行为。有关数组原位更新的细节，可对照 [MuJoCo Python 数据访问说明](https://mujoco.readthedocs.io/en/3.3.7/python.html#basic-usage)。

### 3.1.3 检查数据形状、索引与数值范围

本章模型应显示 `nq=10、nv=9、nu=3`。与第二章相比，机械臂和方块的位置、速度数组长度没有改变，新增的是三个控制输入。位置执行器并没有给机械结构再加三个独立关节。

需要发给机械臂的目标只有三个数，因此统一的目标向量形状是 `(3,)`。它不是整个 `qpos`，更不是把方块位置和四元数一起交给控制器：

```python
target = np.asarray(target, dtype=float)
if target.shape != (3,) or not np.isfinite(target).all():
    raise ValueError("目标必须是按约定顺序排列的三个有限数值")
```

为什么连形状也要检查？因为 `[a, b, c]` 与 `[[a], [b], [c]]` 看起来只是多了一层方括号，在 NumPy 中却分别是 `(3,)` 和 `(3, 1)`。后者与一个 `(3,)` 数组相减，可能通过广播产生 `(3, 3)` 结果，程序未必立刻报错，算出来的却不是三关节误差。

数值检查也不能只比较上下限。`nan` 会让许多比较失去预期含义；`inf` 即使能装进浮点数组，也不是一个可执行目标。先检查所有元素有限，再检查单位、范围和执行器映射。

读取名称失败时，应当停止并报告缺失项。如果使用较底层的 `mj_name2id`，还要特别处理“没找到”返回的负编号。Python 的 `array[-1]` 恰好是合法访问，可能把最后一个执行器误当成你要找的对象。本章通过按名称访问和启动检查，尽早暴露这种错误。

另一个容易反过来的问题是：读取出来的三个关节值，并不总是还能通过修改局部数组写回仿真。例如 `joint_values = data.qpos[qadr]` 使用高级索引得到独立数组，修改 `joint_values` 不等于修改 `data.qpos`。初始化时要显式写回 `data.qpos[qadr] = HOME`；控制运动时，则应写控制目标，让物理计算产生响应。

把“读状态”和“直接改状态”分开，是本章后面回放实验的前提。想让关节运动，就给执行器目标；想恢复一帧过去的画面，才考虑按明确用途写回构型。

## 3.2 发出第一条控制指令

### 3.2.1 理解执行器控制量的含义

先打开 `models/controlled.xml`。它引入桌面与机械臂模型，再为三个关节分别添加位置执行器。肩关节的一项是：

```xml
<position name="shoulder_servo" joint="shoulder" kp="80" kv="4"
          ctrllimited="true" ctrlrange="-1.2 1.2"
          forcelimited="true" forcerange="-8 8"/>
```

在本模型的直接关节传动与默认单位传动比下，控制输入表示目标关节角，单位 rad。因此，写入 `-0.6` 表示要求肩关节跟踪 `-0.6 rad`。它不表示输出 `-0.6 N·m`，也不表示“比当前位置再减 0.6 rad”。[MuJoCo 位置执行器定义](https://mujoco.readthedocs.io/en/3.3.7/XMLreference.html#actuator-position)

为理解作用，可以暂时把未饱和时的伺服关系写成：

```text
关节力矩 ≈ kp ×（目标角 − 实际角）− kv × 实际角速度
```

这是针对本例执行器结构的简化解释，力矩还会受到输出限制。目标误差较大时，位置伺服倾向于加大作用；速度项对运动提供阻尼。运动最终还受质量、重力、接触和数值积分影响，不是给了角度就直接把刚体放过去。

XML 也明确了两种不同范围。`ctrlrange` 限制执行器接收的目标角；`forcerange` 限制它输出的执行器作用，在本例单位传动下对应关节力矩。修改前者不会自动提高驱动能力，修改后者也不会让关节机械限位消失。

本章删掉第二章运动连杆上的 `gravcomp="1"`，让执行器面对实际存在的模型重力；同时在入口 XML 中明确选择 `implicitfast` 积分器。位置伺服的阻尼与数值积分方式会共同影响稳定性，因此不要只复制执行器三行、却忽略模型其余设置。这里使用的增益是教学场景参数，系统调参与稳定性分析留到第 6 章。

这样处理还有一个好处：保持目标不变时，肩和肘可能需要留下小的位置误差，位置项才能产生平衡重力所需的力矩。稍后实测曲线中的这类残差，不应马上被改写成“传感器坏了”。

### 3.2.2 设置单关节目标并观察响应

先执行最简单的单关节实验：

```powershell
.\.venv\Scripts\python.exe control_lab.py --single
```

它只改变底座偏航的参考目标，肩和肘保持原来的参考角。这里的“单关节”是指只有一个目标随阶段变化，不是把另外两个电机关闭。肩和肘仍需要执行器支撑机械臂。

完整程序执行的是往返过程。若只看发送并保持一条目标的核心写法，可以读下面这段：

```python
model, data, qadr, vadr, aids = load_scene()
target = np.array([0.20, -0.6, 1.0])
target = checked_target(model, aids, target)
data.ctrl[aids] = target

for _ in range(100):
    mujoco.mj_step(model, data)

mujoco.mj_forward(model, data)
print("目标角:", target)
print("实测角:", data.qpos[qadr].copy())
```

其中 `load_scene` 和 `checked_target` 来自实验包的 `control_lab.py`，不是 MuJoCo 自带函数。前者建立模型、初始状态和映射；后者验证目标。100 个物理步在本例对应 0.2 s，期间执行器一直使用已设置的目标。

这段代码没有在循环中反复把底座当前位置加上 `0.20`。我们发送的是同一个绝对目标，希望位置逐渐靠近它。如果改成每个步都在上一目标上增加 `0.20`，100 步就会累计成完全不同的命令序列。

观察时，建议同时看初始值、目标值和步进后的实测值。若把目标改成 `0.20 rad`，随后立即读取、却尚未调用任何物理步进，实测角基本没有变化很正常。要求还没有经历物理过程，不能据此判断执行器无响应。

想看画面，可以添加 `--view`。程序会开窗观察约五秒，并保留同样的数据输出。纯数值运行不创建窗口，默认可能很快结束；请以终端给出的输出目录和摘要判断本次运行情况。

### 3.2.3 限位、动作幅度与停止条件

可以接收一个数值，不代表应该接受这个目标。发出命令前，至少检查三个条件：数值和维度正确，关节范围允许，执行器控制范围允许。

本章关节机械范围是 `[-1.5, 1.5] rad`，程序又为其保留 `0.1 rad` 余量；执行器目标范围是 `[-1.2, 1.2] rad`。实际允许目标取两者交集，因此在当前模型中是 `[-1.2, 1.2] rad`。

实验包对不合法目标直接报错，不悄悄截断成另一个目标。如果用户要求 `2.0 rad`，程序不能一边执行 `1.2 rad`，一边只记录原始要求。以后确实要使用限幅时，应分别保存请求值、限幅后发送值和限幅原因。

物理执行期间也要检查。本例在每个 10 ms 控制区间结束后，检查状态数值是否有限、实测关节是否离开允许区域、角速度是否超过本例的保护阈值，以及时间是否按预期前进。发现异常后结束迭代，记录 `state_guard`。

这些检查有明确边界：它们每个控制区间检查一次，不保证捕获五个物理子步中的所有瞬态；`3 rad/s` 等阈值也只是当前教学模型的设定。这里停止的是仿真程序，不能把它当成连接真实设备后的制动措施。

还要预先定义正常结束。程序有总步数预算，也允许用户关闭图形窗口；完整走完记为 `completed`，中途关窗记为 `window_closed`。无论哪一种结束，都不能只靠“Python 进程退出了”推断机器人已经到位。

返回初始姿态还需要额外判断。本章要求最后 50 个测量样本中，三个关节对初始目标的误差绝对值都小于 `0.02 rad`，速度绝对值都小于 `0.02 rad/s`。这组条件与步数完成分别记录，避免把“还在摆动但恰好经过起点”算作稳定返回。

## 3.3 从单关节走向多关节运动

### 3.3.1 固定关节顺序与动作向量

单个角度只有一个位置，三个角度组成向量以后，就必须说明顺序。对本章，`[0.25, -0.5, 0.9]` 的意思始终是底座、肩、肘，而不是按 XML 执行器出现顺序排列。

写入时，程序执行 `data.ctrl[aids] = target`。`aids=[2,0,1]` 将约定顺序转换到真实控制数组：底座目标写入控制项 2，肩目标写入项 0，肘目标写入项 1。读取时用另一组 `qadr`，把实际关节值转换回同一顺序。

如果省略这层映射、直接执行 `data.ctrl[:] = target`，底座的目标就可能被发到肩关节。程序的数组长度仍然都是 3，赋值不会报错，机械臂却做出完全不同的运动。这类错误很难靠“看上去转起来了”发现。

动作接口最好同时固定四个约定：名称顺序、单位、绝对或相对语义、使用时刻。本章三个关节都用 rad，目标是绝对位置，每个控制区间使用一组三个目标。它不是三台电机同时开始新的一条相对移动命令。

多关节实验用一个幅度参数生成整体变化：

```python
HOME = np.array([0.0, -0.6, 1.0])
direction = np.array([1.0, 0.4, -0.4])
target = HOME + amplitude * weight * direction
```

`weight` 从 0 变化到 1，再回到 0。`amplitude=0.25` 时，最大目标变化是 `[0.25, 0.10, -0.10] rad`，对应最远目标 `[0.25, -0.50, 0.90] rad`。这个数值关系可以在运行前手算，再与日志核对。

它只定义关节空间的参考运动。三个关节同时改变，并不意味着末端沿直线移动，也没有保证避开任意障碍物。坐标、运动学与轨迹的关系，会在后面章节逐项展开。

### 3.3.2 组织控制循环与退出逻辑

本章沿用 2 ms 物理步长，但每五个物理步才更新一次参考目标，控制周期因此为 10 ms，即 100 Hz。执行器在物理步进中持续根据当前目标计算作用，而 Python 不需要在每个 2 ms 都生成一个新目标。

![控制区间内指令、物理推进与测量记录的关系](/article-media/robotics-guide-ch03/control-timing.svg)

*图 3-1：区间开始时写入目标，连续推进五个物理步，再读取区间末尾的实际状态。一行记录同时保留两端时间。*

控制循环的骨架是：

```python
for target in target_sequence:
    command_time = float(data.time)
    data.ctrl[aids] = target
    for _ in range(5):
        mujoco.mj_step(model, data)
    mujoco.mj_forward(model, data)
    observation_time = float(data.time)
    # 此处检查状态，再保存本区间的目标和末尾测量。
```

同一目标在整个区间内保持不变。第 0 行对应的是时刻 0 发出的目标，以及约 0.01 s 时测到的结果。把它们写在一行，是为了表示“这条指令作用一个区间后得到的响应”，不是宣称指令和测量发生在完全相同的时刻。

程序一共安排 500 个控制区间，覆盖 2500 个物理步、5 s 仿真时间。图形模式还要同步查看器并等待节拍；没有窗口时不做节拍等待，不能拿现实中程序只运行了很短时间来推翻这五秒的仿真时长。

退出逻辑放在循环中明确处理。窗口关闭时不再追加新目标；状态保护触发时记录原因并停止；预算用完时标记完整结束。循环退出后统一写出已有记录，因此提前结束也能留下被截断的轨迹。

图形模式中对状态的修改使用查看器锁，`sync()` 放在锁外。重型的文件输出集中到运行结束后完成，减少显示同步与磁盘等待混进每个控制区间。不过这仍是教学脚本，不提供严格实时调度保证。

### 3.3.3 比较目标关节值与实际关节值

对关节 j，本章每行误差定义为：`本区间发送的目标角 − 区间末尾测得的关节角`。符号保留下来：正值表示目标在实测值的正方向，负值则相反。

不能只看某个关节当前的绝对角度。肩关节本来就在 `-0.6 rad` 附近，数字比底座大，并不说明它误差更大。要把每个测量与对应关节、对应时段的目标相减。

本章保存两类结果。**跟踪误差**看全过程，反映运动时的滞后和保持阶段的残差；**返回误差**只看最后要求回到初始姿态后的表现。前者不能代替后者，后者也不能证明整段过程没有偏差。

全过程的一个摘要量是每个关节的均方根误差，写作 RMSE：先对每行误差平方，求平均，再开平方。它保留角度单位，但不会告诉你误差发生在哪一秒，所以还需要曲线。

例如，把幅度从 0.15 rad 增大到 0.35 rad，底座需要在相同一秒内转过更远距离。如果控制器和时间安排不变，运动过程的滞后可能增大；最后留足时间返回以后，终点误差却可能仍接近原来水平。两项结果同时成立，并不矛盾。

保持阶段的小残差也有物理含义。撤掉重力补偿后，位置伺服需要借助误差产生支撑作用。本例实测肩关节的最终位置误差约为 `-0.01085 rad`，肘关节约为 `-0.00269 rad`，而底座误差非常接近零。先检查受力、控制律和限幅，再决定是否修改参数，不能为了让日志好看就把实测值替换成目标值。

这套实验还没有定义物体操作任务。`returned_and_settled=true` 只说明规定关节在规定采样点满足返回条件，不说明机械臂抓住过方块，也不说明任意末端误差都小于某个毫米数。

## 3.4 保存与回放一次实验

### 3.4.1 记录动作、状态、时间与配置

每次运行结束，终端都会给出一个新的 `runs/<UTC时间>/`。程序没有覆盖上一次的记录，所以调整幅度后，可以把两份目录并排比较。目录名只负责区分运行，真正解释实验的是目录内的文件。

| 文件 | 本章保存的内容 | 为什么需要它 |
| --- | --- | --- |
| `summary.json` | 版本、模型哈希、名称顺序、映射、幅度、时序、终止原因与误差摘要 | 确定实验条件和结果口径 |
| `trajectory.csv` | 每个区间的目标、区间末尾的实际位置和速度、误差、末端世界位置 | 用表格或其他程序检查全过程 |
| `states.npz` | 初始与各区间末尾的位置、速度、时间，目标序列及初始积分状态 | 支持数值回放与画面重放 |
| `tracking.svg` | 由绘图程序另行生成的跟踪曲线 | 把数值变化放在同一时间轴上观察 |

CSV 一行从 `tick`、`command_time_s`、`observation_time_s` 和阶段名称开始，随后按固定关节顺序保存目标、位置、速度和误差。字段名保留单位，例如 `target_rad_base_yaw` 与 `v_rad_s_shoulder`，不会只写一列含义不明的 `value`。

想检查时间对齐，可以先看第一行和第二行。第一行命令时间约为 0，观察时间约为 0.01 s；第二行约为 0.01 s 与 0.02 s。两行不能有相同时间却声称记录了两个新的执行区间，也不应把现实时间戳当作这里的仿真时间。

完整运行有 500 行 CSV 数据，加一行表头。NPZ 另存了最初时刻的状态，所以其时间、位置和速度数组有 501 个样本，而目标数组仍然只有 500 行。这是有意保留的关系：500 条区间命令，把系统从初始样本推进到第 500 个末尾样本。

模型哈希覆盖本包使用的三份 XML。只记录入口 `controlled.xml` 还不够，因为它包含的 `tabletop.xml` 和 `drop.xml` 同样会影响结果。保存目标序列也不能替代保存这些定义：同一组角度交给质量和力矩限制不同的机械臂，不会自动产生同一条轨迹。

为了便于读懂，本章先把样本收集到内存，在正常完成、主动关窗或状态保护退出后统一保存。它没有实现崩溃恢复：按 Ctrl+C、强制终止进程或发生未预料的引擎异常时，不保证留下完整文件。以后跑长时间实验，应采用周期刷新或分块写入，并标记最后完整区间；不要因为已经创建了目录就认为所有数据都安全落盘。

打开 NPZ 时使用 `allow_pickle=False`，这些记录只包含数值数组，不需要加载 Python 对象。它与 CSV 一样，是我们明确约定的数据格式，而不是把整个运行中的进程打包保存。

### 3.4.2 绘制轨迹和跟踪误差曲线

从终端复制刚生成的真实输出目录，设置一个变量。下面的目录名是提示文字，必须替换为你自己的那份：

```powershell
$runDir = 'runs/把这里换成实际生成的目录名'
.\.venv\Scripts\python.exe plot_run.py --run $runDir
```

程序生成 `tracking.svg`。它只读取记录、计算误差并绘图，不再推进仿真。由同一份记录反复画图，也不应该让机械臂“再执行一遍”才得到原来的结果。

![幅度为0.15弧度时三关节的目标、实测位置与区间跟踪误差](/article-media/robotics-guide-ch03/tracking-small.svg)

*图 3-2：本章实际运行的 0.15 rad 多关节实验。左列是目标与实测值，右列是本区间目标减去区间末尾实测值；绿色背景标出回程结束后的稳定观察阶段。图内坐标用英文关节名与 SI 单位，便于对应原始字段。*

左列目标用阶梯线绘制，因为每个目标会保持一个 10 ms 区间。测量值按各自的测量时间绘制。不能为了让两条线看起来更接近，就把实测时间整体往前挪一格。

右列误差是在每个区间末尾计算的，使用的是该区间实际发送并保持的目标。这是本章定义的离散跟踪指标。如果以后需要与连续时间理想轨迹比较，应当另外定义那条参考轨迹和采样时刻，不能混用两种误差。

看图时先找阶段，再找误差形状。0 到 0.5 s 是初始保持；0.5 到 1.5 s 向外运动；1.5 到 2.5 s 保持；2.5 到 3.5 s 回程；之后继续维持初始目标。若目标还没开始变化，关节就明显跑向另一处，先查初始化、控制映射和接触，不要马上把原因归给轨迹规划。

运动段的滞后、停止后的振荡、保持段的偏差，也要分开解释。把它们压成一个全过程平均数，会失去最有助于排错的信息。例如，平均误差很小的实验，仍可能有某一个瞬间的大幅突跳。

同样的道理，图的纵轴范围会影响视觉感受。如果绘图工具自动把某个关节的纵轴缩到非常窄，小的残差也会显得很醒目。请先读坐标数字和单位，再比较幅度。图 3-2 保留各关节的实际量级，不用“线条是否重合”代替数值判断。

### 3.4.3 回放动作与重放状态的区别

现在用同一份记录做两件看起来相似、计算过程却不同的事。

第一件是**动作回放**：恢复实验开始时的状态，再把保存的目标按照原控制周期重新交给执行器，调用物理步进，得到一条新的响应轨迹：

```powershell
.\.venv\Scripts\python.exe replay.py --run $runDir --mode actions
```

回放器核对三份模型的哈希以及 MuJoCo、NumPy 版本，再恢复保存的初始积分状态。它不是只把关节角设回起点，还利用 `mj_getState`、`mj_setState` 和 `mjSTATE_INTEGRATION` 保存、恢复本例所需的引擎积分状态。状态范围的含义应查 [MuJoCo 状态接口](https://mujoco.readthedocs.io/en/3.3.7/APIreference/APIfunctions.html#mj-getstate)。

本章在同一台机器、同一套数值库与模型下，重新执行 500 条区间目标，关节位置相对于原记录的最大差为 0。这个结果证明本次条件下回放重现了关节轨迹，不是跨平台逐位一致的承诺。真实机器人还有测量、通信、温度和接触变化，更不能照此假设每次执行完全一样。

接着故意改变起点：

```powershell
.\.venv\Scripts\python.exe replay.py --run $runDir --mode actions --perturb-yaw 0.1
```

它在恢复初始积分状态后，把底座初始角增加 0.1 rad，再执行原来的目标序列。目标依旧是绝对角度，因此控制器会试图拉回原目标；前面一段响应已经不同，最后仍可能回到相近终点。

回放输出把“初始差”和“物理步进后的最大差”分别列出。只看到 0.1 rad 的初始差，不能证明后续轨迹不同；本章实测步进后最大关节差约为 `0.09448 rad`，这才是重新执行过程发生差异的直接证据。

第二件是**状态重放**：依次把记录的关节与方块构型、速度和时间写回，再刷新用于显示的派生量：

```powershell
.\.venv\Scripts\python.exe replay.py --run $runDir --mode state --view
```

这个分支不调用 `mj_step` 推进物理。它能帮助你换个视角检查过去的姿态，但画面之所以沿着原路径走，是因为程序逐帧指定了状态。不能把它当作“同一组动作再次产生了这条路径”的证据。

本例状态重放也没有恢复每一帧完整的接触力、控制器历史或所有传感器内部状态。`mj_forward` 根据当前帧重新算出的量，不应自动被称作当时实际记录的历史值。如果想恢复任意中间时刻继续计算，需要更完整的积分状态，以及任务程序、随机数和外部模块的状态约定。

两种模式可以按用途选择：想检查命令是否能在相同条件下重现响应，用动作回放；想检查某一时刻机械臂摆在哪里，用状态重放。文件相同，结论需要跟着计算方式走。

## 3.5 实验 完成一段可追溯的关节运动

### 3.5.1 编写回到初始姿态的程序

把前面各部分接起来，完成一次“初始保持 → 向外运动 → 保持 → 回程 → 稳定观察”。本次不要求末端到达某个世界坐标，也不操作方块，只要求关节按照已定义的参考运动往返。

先写下初始目标：底座 0 rad，肩 -0.6 rad，肘 1.0 rad。程序必须在开始时设置实际初始构型与三个执行器的保持目标，并确认没有遗留速度。接着，根据仿真时间生成参考：

| 时间段 | 阶段 | 本段参考目标 |
| --- | --- | --- |
| 0–0.5 s | 初始保持 | 三个关节维持 HOME |
| 0.5–1.5 s | 向外运动 | 权重从0增加到1，逐区间改变目标 |
| 1.5–2.5 s | 中间保持 | 维持最远目标 |
| 2.5–3.5 s | 回程 | 权重从1减回0 |
| 3.5–5.0 s | 稳定观察 | 持续保持HOME，检查响应 |

本章参考用最简单的分段线性变化。它避免了直接把整段幅度一次跳到目标，但在阶段边界仍有参考速度的切换，不能称为已经满足速度、加速度连续性的完整轨迹规划。后面的轨迹章节会继续处理这些问题。

执行多关节基线：

```powershell
.\.venv\Scripts\python.exe control_lab.py
```

默认幅度为 0.25 rad。终端输出 `complete`、`returned_and_settled`、最终关节误差和全过程 RMSE。两种布尔值都应有清楚的定义：前者看是否完整执行500个区间，后者还看最后50个样本是否满足本例位置与速度条件。

不要把最后一个目标重新写成 HOME 就立即结束。那只是发出了返回请求，实际机械臂可能还没到。程序特意保留最后一段稳定观察时间，用新的测量判断是否已经接近起点并且运动足够慢。

如果把脚本改成新任务，也应保留这种收尾结构：先发出收尾目标，再观察结果，最后记录结束原因。具体到抓取任务，收尾还需要检查物体与夹爪；本章只处理关节，先不借用“任务成功”这个更宽的词。

### 3.5.2 改变目标幅度并比较执行结果

现在做一个控制变量实验。模型、增益、时间安排和起点全部不变，只改变往返幅度：

```powershell
.\.venv\Scripts\python.exe control_lab.py --amplitude 0.15
.\.venv\Scripts\python.exe control_lab.py --amplitude 0.35
```

保留两个输出目录，分别生成跟踪图。幅度改变后，三关节最远目标分别为：

| 幅度 | 底座目标 | 肩目标 | 肘目标 |
| --- | ---: | ---: | ---: |
| 0.15 rad | 0.15 rad | -0.54 rad | 0.94 rad |
| 0.35 rad | 0.35 rad | -0.46 rad | 0.86 rad |

这张表来自 `HOME + amplitude × direction`，可以在运行前算出。它不是执行后的测量结果；测量应到对应目录中读取。

![幅度为0.35弧度时三关节的目标、实测位置与区间跟踪误差](/article-media/robotics-guide-ch03/tracking-large.svg)

*图 3-3：其他设定不变，把幅度增加到0.35 rad后的实际曲线。比较时同时查看坐标范围和数值摘要，避免把自动缩放后的线条形状当成等比例差异。*

下面是本章实际运行的结果，RMSE 使用前文定义的“区间目标减区间末尾测量”，覆盖全部500行：

| 幅度 | 底座RMSE / rad | 肩RMSE / rad | 肘RMSE / rad | 完整执行 | 满足稳定返回条件 |
| --- | ---: | ---: | ---: | --- | --- |
| 0.15 rad | 0.005209 | 0.011087 | 0.003387 | 是 | 是 |
| 0.35 rad | 0.012155 | 0.012079 | 0.005542 | 是 | 是 |

两次实验的最终肩误差都约为 -0.010851 rad，最终肘误差都约为 -0.002695 rad。底座全过程误差随幅度明显增加，但最后仍能回到原始目标附近。这说明“运动中跟得多紧”与“最终能否稳定返回”需要分别报告。

这组对照支持的是当前模型、相同时间预算下的观察。它没有证明所有机器人都按这个比例变化，也没有区分惯量耦合、控制带宽与参考速度各自贡献多少。若要研究原因，下一步应保持其余条件，再改变运动时长或控制参数，做新的对照。

本次也没有测完整物体任务成功率。桌上方块只是保留场景中的自由物体，关节返回结果不等于方块搬运结果。等后面加入夹爪和任务状态机，才会有那一层评价。

### 3.5.3 诊断无响应、突跳与越界问题

最后做一次排错练习。遇到现象时，沿着“目标生成 → 名称映射 → 执行器 → 物理更新 → 实测记录”逐段检查，尽量找到第一处与预期不同的位置。

| 现象 | 优先检查 | 能留下的证据 |
| --- | --- | --- |
| 目标变了，关节完全不动 | 是否真的推进物理、执行器是否存在、是否写对控制项 | `nu`、执行器映射、前后时间与位置 |
| 底座命令让肩动了 | 关节约定顺序与XML执行器顺序是否混用 | 名称到`aids`的映射表 |
| 一开始三个关节都冲向零 | 初始化是否只设置了`qpos`，却遗漏保持目标 | 第一个控制区间的三项目标 |
| 重复调用后越转越远 | 是否把绝对目标误写成累加增量 | 连续目标序列与最大变化 |
| 画面瞬间换姿态，速度却没有对应过程 | 是否直接修改了`qpos` | 代码路径与物理时间记录 |
| 关节不断振荡，力矩频繁到上限 | 增益、阻尼、时间步长和积分器是否与模型匹配 | 位置、速度、控制作用与模型版本 |
| 发了很大的目标但实际被限制 | 程序范围、控制范围、力矩范围分别是什么 | 请求、实际发送值和拒绝原因 |
| 显示流畅但日志错位 | 是否把上一时刻状态写成当前响应，是否保存了数组引用 | 两端时间、刷新派生量的位置 |
| 已执行完，但返回判断失败 | 误差是否超容差，或者速度仍然较大 | 最后50个位置与速度样本 |
| 回放看起来完全一样 | 使用的是动作回放还是直接写回状态 | 回放模式、是否调用物理步进 |

“突跳”还需要区分参考突跳与实际状态突跳。目标一下改变0.2 rad，实际关节仍应经历动力学响应；如果实际位置在不推进时间的情况下被写成另一个值，那是状态赋值。不要把两种情况都归成“电机转得太快”。

本章调试时也观察过：将这组位置伺服直接搭到原来的 Euler 积分设置上，可能出现高频运动和力矩饱和。随文版本明确使用 `implicitfast`，并重新通过数值实验。它提醒我们，添加执行器改变了系统的数值特性，不能把第二章静态模型能运行当作控制参数必然合适的证据。

完成以下六项练习，再运行自检。

**练习一：查清映射。** 为什么本模型的底座关节编号是1、位置地址是7、速度地址是6，执行器编号却是2？如果新增一只自由物体，哪些数字可能变化？

**练习二：解释零目标。** 位置执行器收到0，是否意味着不施加作用？如果肩关节已经在-0.6 rad，写入0会要求它做什么？

**练习三：核对时间。** 一个控制区间包含5个2 ms物理步。500行区间记录覆盖多长仿真时间？为什么NPZ有501个状态样本？

**练习四：计算参考。** 幅度0.35 rad、方向向量`[1,0.4,-0.4]`、HOME为`[0,-0.6,1]`，最远目标是什么？这些是实测值吗？

**练习五：判断返回。** 最后一帧位置误差只有0.005 rad，但角速度为0.3 rad/s，是否满足本章稳定返回条件？全过程RMSE能否代替最后50次检查？

**练习六：选择回放。** 同一份记录用状态重放得到一致画面，是否证明动作可复现？如果改变初始关节角后重跑原动作，应比较哪些量？

**参考分析**

1. 三类编号与两类数组地址分别服务于不同结构；自由物体占用的位置与速度分量数也不同。新增模型元素可能改变数组布局，应重新解析名称映射，不能手工补一个固定偏移就认为所有模型都适用。
2. 0 rad是绝对位置目标，不是“关闭”。肩关节会被要求向零位运动，执行器作用还取决于实际位置、速度和限制。
3. 控制周期0.01 s，500行覆盖5 s；另存初始样本后，状态数组比区间目标多一行。
4. 最远目标为`[0.35,-0.46,0.86] rad`。它们来自参考定义，真正的响应要看后续测量。
5. 不满足。本章还要求最后50个样本的速度绝对值小于0.02 rad/s。RMSE只摘要全过程，不能替代末尾窗口条件。
6. 不能。直接写回状态本来就会沿记录的构型显示。动作复现需要恢复起点、重新推进物理，比较对应时间的实际关节轨迹；改变初态时，还应把初始差与步进后差分开记录。
